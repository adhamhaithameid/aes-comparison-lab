    AES Comparison Lab

    Engineering, Performance, and Security — how two AES-128 implementations were built, tested, measured, and turned into an interactive learning site.

    The Problem

    Teaching cryptography usually forces a choice between two bad options. Textbooks describe AES as abstract mathematics — substitutions, permutations, finite-field arithmetic — with no way to watch it happen. Production code hides every step behind a library call, so a learner sees EVP_EncryptUpdate() and nothing else. In between sits the part nobody builds: a correct, instrumented, deliberately slow implementation that exposes each transformation, paired with a real library doing the same work, so the gap between them can be measured rather than asserted.

    That gap is the project's subject. A from-scratch AES-128 written in clear, table-driven C++ sits next to OpenSSL's AES-128-ECB and AES-128-GCM. Both pass the same NIST known-answer tests, which proves correctness is not the differentiator — correctness is the baseline. What differs is performance, memory, and what each one is actually allowed to protect. The site exists to make that difference visible, measurable, and honest about its own limits.

    Question 1

    Can an educational AES implementation be made provably correct against published NIST vectors while staying readable enough to step through?

    Question 2

    What is the real, measured cost of writing crypto by hand instead of using a hardware-accelerated library?

    Question 3

    Where is the line between correct and safe to use, and can a site teach that line without overstating either side?

    Architecture

    The system is split along a single hard boundary: a native C++ core that does the cryptographic and measurement work, and a static web front end that only ever reads exported results. There is no server, no runtime API, and no build step in production — the browser fetches data files that the benchmark step already wrote.

          Implementation

          Implementation A — From scratch

          Educational

          A byte-oriented AES-128 written directly from FIPS 197. SubBytes, ShiftRows, MixColumns, and AddRoundKey are separate, named functions; the key schedule expands 44 words with explicit GF(2⁸) arithmetic; encryption and decryption are distinct paths. Nothing is optimized: no precomputed T-tables, no AES-NI intrinsics, no hand-tuned assembly. That is deliberate — the point is that a reader can follow one block from plaintext to ciphertext without a jump table.

            Implementation B — OpenSSL

            Production

            The same AES-128 through OpenSSL's EVP interface, exercised in two modes: raw ECB for a like-for-like comparison with the core, and GCM for authenticated encryption. OpenSSL dispatches to ARMv8 cryptographic instructions at runtime, so this path measures what a vetted library actually does on modern hardware — including the authentication work the from-scratch path does not perform at all.

                          Security & Limitations

                          This project is for education, not protection. The from-scratch implementation is an unauthenticated block cipher with no defence against timing or power analysis. Do not use it to encrypt anything you care about.

                          ECB and GCM are not interchangeable

                          The benchmark table lists them side by side because they run the same cipher, and that is the only axis on which they are comparable. They do not provide the same security, and nothing on this site should be read as if they did.

                          QuestionAES-ECBAES-GCM
                          Does identical plaintext produce identical ciphertext? Yes — that is ECB No — nonce-dependent
                          Can a modified ciphertext be detected? No Yes — tag check
                          Safe for real data? No Yes, with nonce discipline
                          Measured cost of that safety — —

                          GCM's remaining failure mode is nonce reuse: encrypting two different messages under the same key with the same nonce destroys confidentiality for both. That risk is inherent to the mode, not to this implementation, and it applies to production code too.

                          Limitations of this project

                          • From-scratch AES is unauthenticated — no tag, no tamper detection.
                          • It is not constant-time; table lookups leak through timing.
                          • No defence against power, cache, or electromagnetic side channels.
                          • ECB mode is used for comparison only and reveals plaintext patterns.
                          • Only a subset of the NIST GCM vector files was exercised.

                          Limits of the measurements

                          • Single platform: one Apple M1, one OS, one compiler.
                          • No repeated independent runs — figures carry run-to-run variance.
                          • RSS includes process and library overhead, not just algorithm memory.
                          • Micro-benchmarks at 16 B are dominated by call overhead.
                          • Results do not transfer to x86 AES-NI or to CPUs without crypto extensions.

                          Conclusion & Links

                          The project set out to measure the distance between writing AES and using AES, and the measurement is unambiguous. The from-scratch implementation is correct — it clears the same published vectors OpenSSL clears — and it is roughly three orders of magnitude slower, because correctness was never the hard part. A vetted library on hardware built for the job is. The practical lesson is the one the whole comparison exists to deliver: use authenticated encryption, and use a vetted library to get it.

                          The site is the second deliverable. Everything on it — test counts, throughput, memory, environment — is derived from files in the repository rather than typed into markup, so the page cannot drift away from the data that produced it. That constraint is the difference between a report and evidence.
