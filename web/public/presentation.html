AES Implementation Comparison

Two approaches to AES-128: a from-scratch educational cipher vs. a production OpenSSL wrapper.

Educational lab — not for production use unless noted.

Implementation A — Scratch AES-128 Implementation B — OpenSSL AES-128-GCM

What is AES?

  • Symmetric block cipher — FIPS 197 (NIST, 2001).
  • 128-bit block size; keys of 128 / 192 / 256 bits.
  • AES-128 uses 10 rounds: SubBytes, ShiftRows, MixColumns, AddRoundKey.
  • Raw AES gives confidentiality only — no integrity, no authentication.
  • Real systems need a mode of operation (GCM, CBC, CTR, …) and often a MAC.

Implementation A — Scratch AES-128

What it is

  • Written from scratch in C++17 (src/aes_core.hpp/.cpp).
  • Every transform exposed for learning and validation.
  • Raw block cipher: encrypts 16-byte blocks.

Provides

  • FIPS 197 known-answer tests pass.
  • NIST CAVP ECB KATs (GFSbox, VarTxt, VarKey, MMT).
  • Cross-validation vs OpenSSL on 1000 random blocks.
  • CLI: aes_scratch kat / encrypt-block / roundtrace.

No authentication, no replay protection, no padding — education/validation only.

Implementation B — OpenSSL AES-128-GCM

What it is

  • Wrapper around OpenSSL EVP interface (src/aes_gcm_openssl.hpp/.cpp).
  • Authenticated encryption: confidentiality + integrity.
  • Hardware-accelerated (AES-NI / ARMv8 crypto).

Provides

  • Fresh random nonce per encryption.
  • 128-bit authentication tag verified before plaintext release.
  • File encryption CLI: aes_openssl keygen / encrypt / decrypt / selftest.
  • NIST CAVP GCM KATs incl. official FAIL cases.

Use this (or libsodium/mbedTLS) for real applications.

Usage — CLI

Implementation A (block cipher demo)

./build/aes_scratch kat
./build/aes_scratch encrypt-block --key 000102030405060708090a0b0c0d0e0f --input 00112233445566778899aabbccddeeff

Implementation B (file encryption)

./build/aes_openssl keygen mykey.txt
./build/aes_openssl encrypt mykey.txt secret.txt secret.enc
./build/aes_openssl decrypt mykey.txt secret.enc secret_dec.txt

Security model

Impl A risks

  • Ciphertext tampering undetected.
  • Replay attacks possible.
  • ECB-style misuse if chained naively.

Impl B guarantees

  • Confidentiality + integrity (GCM).
  • Tag verified before plaintext release.
  • Nonce uniqueness enforced by design.

Rule of thumb: learn with A, ship with B (or libsodium/mbedTLS).

Bonus: MixColumns micro-benchmark (Python)

The repo also includes a pure-Python AES-128 comparing two MixColumns strategies:

  • Version A — xtime operations.
  • Version B — precomputed x2 / x3 lookup tables.

Both match the FIPS 197 test vector; tables are faster at scale (trade-off: extra memory).

  • 1,431 automated checks (FIPS 197 KATs, NIST CAVP ECB/GCM, round-trips 0 B to 10 MB, tampering, cross-validation).
  • Sanitizers: ASan + UBSan, 0 findings.
  • Benchmarks: 3 implementations x 5 sizes x 3 ops (355 data points).

Summary

  • Impl A = transparent, educational, no auth — for learning and validation.
  • Impl B = authenticated, accelerated, production-ready — for real data.
  • Same AES-128 core; difference is mode, integrity, and performance.
  • Always: learn with A, ship with B (or libsodium/mbedTLS).
