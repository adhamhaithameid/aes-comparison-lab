    What If? — AES Security Lab

    Experiment with 12 security scenarios to understand AES vulnerabilities and best practices

    Educational JavaScript implementation — NOT for production use. All scenarios use synthetic data only. No real encryption keys or sensitive data are used.
    1

    Modified Ciphertext (Bit Flip)

    What happens if an attacker flips a single bit in AES-GCM ciphertext?

    Conditions: AES-128-GCM encrypted message. Attacker flips bit 3 of byte 0 in the ciphertext.
    Bit 3
    Security Lesson: AES-GCM's authentication tag detects any modification. A single bit flip causes decryption to fail completely — the attacker cannot selectively modify ciphertext.
    Mitigation: Always use authenticated encryption (GCM, CCM, or Encrypt-then-MAC). Never use unauthenticated modes like ECB or CBC without a MAC.

    2

    Modified Authentication Tag

    What if an attacker modifies the GCM authentication tag instead of the ciphertext?

    Conditions: AES-128-GCM encrypted message. Attacker flips bits in the 16-byte authentication tag.
    Security Lesson: The authentication tag is a cryptographic checksum over the ciphertext and AAD. Any modification — even a single bit — will cause verification to fail with overwhelming probability.
    Mitigation: The tag must be transmitted securely alongside the ciphertext. Use constant-time comparison when verifying tags.

    3

    Wrong Key

    What happens when you try to decrypt AES-GCM ciphertext with the wrong key?

    Conditions: Message encrypted with Key A. Attacker attempts decryption with Key B (single bit different).
    Security Lesson: AES has no "partial decryption" — a wrong key produces completely random-looking output. With GCM, the authentication tag will also fail, preventing any information leakage.
    Mitigation: Use strong, randomly generated keys. Implement proper key management with rotation and secure storage.

    4

    GCM Nonce Reuse

    Why is reusing a GCM nonce with the same key catastrophic?

    Conditions: Two different messages encrypted with AES-128-GCM using the same key and nonce.
    Security Lesson: Nonce reuse in GCM leaks the XOR of the two plaintexts and allows forgery of authentication tags. This completely breaks both confidentiality and authenticity. The GHASH key can be recovered.
    Mitigation: Use a counter-based nonce (guaranteed unique) or random 96-bit nonces (collision probability negligible). Never reuse a nonce with the same key.

    5

    AES-128 vs AES-256

    How do AES-128 and AES-256 compare in security and performance?

    Conditions: Synthetic benchmark data comparing key sizes.
    Security Lesson: AES-256 provides a larger security margin against quantum attacks (Grover's algorithm halves effective key size: 128→64, 256→128). AES-128 is still considered secure against classical attacks.
    Mitigation: Use AES-256 for long-term data protection or post-quantum preparation. AES-128 is acceptable for ephemeral data.

    6

    Input Size Scaling

    How does AES performance scale with input size?

    Conditions: Real benchmark data from 16 bytes to 10 MB.
    Security Lesson: Small inputs are dominated by overhead (key setup, function call). Large inputs approach the raw AES throughput. This is why hardware acceleration (AES-NI) matters most for bulk data.
    Mitigation: For small messages, the performance difference between implementations is negligible. For bulk data, always use hardware-accelerated implementations.

    7

    Hardware Acceleration Detection

    How much does AES-NI hardware acceleration improve performance?

    Conditions: Comparing scratch C++ (no AES-NI) vs OpenSSL (with AES-NI).
    Security Lesson: AES-NI provides 10-100x speedup over software implementations. It also provides better side-channel resistance since the CPU handles AES in dedicated hardware.
    Mitigation: Always use hardware-accelerated AES when available. Check CPU flags before falling back to software implementations.

    8

    Incorrect AES Implementation

    What if SubBytes uses a deliberately broken S-box? Round-trips pass but KATs fail.

    Conditions: AES-128 with S-box where S[0x00] = 0x00 (should be 0x63).
    Security Lesson: A broken S-box still produces a bijection (round-trips work), but the output is completely wrong. Known Answer Tests (KATs) from FIPS 197 would catch this immediately. Always validate against test vectors.
    Mitigation: Always test against FIPS 197 Appendix B and C test vectors. Use established libraries (OpenSSL, libsodium) rather than rolling your own crypto.

    9

    Authentication Failure Mid-File

    What happens when authentication fails partway through decrypting a large file?

    Conditions: 1 MB file encrypted with AES-GCM. Bit flip introduced at 50% of the file.
    Security Lesson: GCM authentication is all-or-nothing. If any bit is wrong, the entire decryption fails. You cannot recover partial data — this is by design to prevent oracle attacks.
    Mitigation: For large files, consider chunking with separate authentication per chunk, or use a streaming AEAD. Always verify the tag before using any decrypted data.

    10

    ECB Pattern Leakage

    Why does ECB mode leak patterns in encrypted data?

    Conditions: A 16×16 pixel image encrypted with AES-ECB. Identical plaintext blocks produce identical ciphertext blocks.
    Security Lesson: ECB encrypts each block independently. Identical plaintext blocks → identical ciphertext blocks. This preserves patterns in the data. The famous "ECB penguin" demonstrates this visually.
    Mitigation: Never use ECB for data with patterns. Use GCM, CBC (with random IV), or CTR mode. Always use authenticated encryption.

    ← Previous: Mid-File | Next: Variance →

    11

    Memory/Timing Measurement Variance

    How much do memory and timing measurements vary between runs?

    Conditions: Real benchmark data with 10 repetitions per measurement.
    Security Lesson: Timing variance can leak information about keys (timing attacks). Constant-time implementations are essential. Memory measurements vary due to OS paging, allocator behavior, and ASLR.
    Mitigation: Use constant-time implementations (OpenSSL, libsodium). Run benchmarks multiple times and report variance. Isolate benchmark processes from other workloads.

    12

    Implementation Selection Decision Guide

    Which AES implementation should you choose for your use case?

    Conditions: Answer questions to get a recommendation.
    Security Lesson: There is no "best" AES implementation — only the best fit for your constraints. Always prefer established, audited libraries over custom implementations.
    Mitigation: Use OpenSSL or libsodium for production. Use AES-GCM for authenticated encryption. Enable hardware acceleration when available.
